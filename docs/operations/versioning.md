# Versioning Convention — CircleGuard

CircleGuard uses **Semantic Versioning** (SemVer 2.0) automated through Conventional Commits.

---

## Tag Convention

Tags follow the format: `vMAJOR.MINOR.PATCH`

Examples:
- `v1.0.0` — initial production release
- `v1.1.0` — new feature added
- `v1.1.1` — bug fix
- `v2.0.0` — breaking API change

Tags are created on the `master` branch only. Feature branches and PRs do not produce version tags.

---

## Bump Rules

The bump level is determined by reading the Conventional Commits message history since the last tag:

| Commit Type | Version Bump | Example Commit Message |
|-------------|-------------|------------------------|
| `BREAKING CHANGE` footer or `!` in type | **MAJOR** | `feat!: remove v1 API endpoints` |
| `feat:` | **MINOR** | `feat: add JWT refresh token support` |
| `fix:`, `chore:`, `docs:`, `refactor:`, `test:`, `ci:`, `perf:` | **PATCH** | `fix: resolve kafka consumer timeout` |
| No conventional commits since last tag | **PATCH** (default) | (any non-conforming message) |

If multiple bump levels are present in the same release, the highest wins (MAJOR > MINOR > PATCH).

---

## How to Trigger a Release

Releases are triggered automatically by the master pipeline when a push to `master` is detected:

1. Developer merges PR to `master`.
2. Jenkins `circleguard-master` job starts automatically.
3. After all tests pass and the production deployment is approved, `ci/semver.sh` runs:
   - Reads all commits since the last `v*` tag.
   - Calculates the new version number.
   - Creates a Git tag via GitHub API.
   - Generates `RELEASE_NOTES_vX.Y.Z.md`.
4. `ci/release-notes.sh` groups commits by type (feat / fix / chore / ...).
5. A GitHub Release is published automatically via `gh release create`.

---

## Generated Artifacts

Each release produces:
- A **Git tag** `vX.Y.Z` on the merge commit.
- A **`RELEASE_NOTES_vX.Y.Z.md`** file committed to the repository root (generated by `ci/release-notes.sh`).
- A **GitHub Release** at `https://github.com/lilmagusa17/circle-guard-public/releases/tag/vX.Y.Z` with the release notes as the body.

## Viewing Release History

```bash
# List all version tags, newest first
git tag --list 'v*' --sort=-version:refname | head -10

# Show commits included in a specific release
git log v1.1.0..v1.2.0 --oneline

# Show the latest release tag
git describe --tags --abbrev=0
```

GitHub Releases page: https://github.com/lilmagusa17/circle-guard-public/releases

---

## Pipeline Version Validation

`ci/semver.sh` reads commits using the following logic:

```bash
# Get the last semver tag
LAST_TAG=$(git describe --tags --abbrev=0 --match='v*' 2>/dev/null || echo "")

# Determine bump based on commit messages
if git log contains "BREAKING CHANGE" or "!:" → MAJOR bump
elif git log contains "^feat:" → MINOR bump  
else → PATCH bump
```

If the working tree has no reachable `v*` tag (first release), the version starts at `v0.1.0`.

If a commit message does not follow Conventional Commits format, it is treated as a patch-level change. It does not block the pipeline, but it will not trigger a minor or major bump.

---

## Manual Tagging (Emergency)

If `ci/semver.sh` fails and a manual tag is needed:

```bash
# Tags must follow vMAJOR.MINOR.PATCH — no suffixes, no pre-release notation
git tag v1.2.3
git push origin v1.2.3

# Then manually create the GitHub Release
gh release create v1.2.3 --title "v1.2.3" --notes-file RELEASE_NOTES_v1.2.3.md
```

Tags that violate the `vX.Y.Z` convention (e.g., `v1.2`, `1.2.3`, `v1.2.3-rc1`) are not recognized by `ci/semver.sh` as base tags and will be ignored when calculating the next version.
